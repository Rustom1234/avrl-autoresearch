# S10: Training Frameworks and Implementability (reward hooks, async/colocated vLLM, memory)

## 1. What this angle contributes to the thesis (3 sentences)

The framework survey shows the allocator is not a new training loop but a plug-in: TRL's `reward_funcs` list, OpenRLHF's `--reward.remote_url` (returns a rewards/scores/extra_logs dict), and verl's `custom_reward_function.path/name` hook already treat "how to score this rollout" as a per-sample, swappable decision, so a learned allocator can sit inside the existing reward call rather than requiring new infrastructure. Async and colocated vLLM modes (TRL's `vllm_mode="server"` vs `"colocate"`, OpenRLHF's `--train.async_enable`, SkyRL's "fully async RL with in-flight weight updates") already decouple generation latency from scoring latency, the precondition for paying for an expensive verifier on some rollouts without stalling the rest. Concrete memory numbers (Unsloth: 54.3GB vs 510.8GB for a 20K-context, 8-generation GRPO step; TRL's default 0.3 vLLM GPU-memory-utilization reserved to avoid OOM) show a 7B GRPO run on one A100 40GB is already memory-constrained before any verifier is added, so the allocator's own footprint (a small classifier or GP) is a real design constraint, not a footnote.

## 3. Supports vs threatens the thesis claim

**Supports:** Reward hooks in the frameworks surveyed already expose per-sample, per-rollout-group granularity (TRL's `reward_weights` and multi-objective aggregation modes, OpenRLHF's per-sample rewards/scores dict, verl's per-`solution_str` `compute_score` call), exactly where an allocator would intervene, so "pay for the expensive verifier or accept a cheap proxy" is a wrapper around an existing function signature, not new trainer code. Async generation already exists in TRL (server mode), OpenRLHF (`async_enable`), and SkyRL (in-flight weight updates), so the allocator needs no new concurrency infrastructure, only a routing policy. DAPO's dynamic sampling is already merged into verl-based pipelines, and VIP is a learned, in-training, per-prompt budget allocator now under ICLR 2026 review, evidence that budget-aware rollout logic is implementable and useful, not purely theoretical.

**Threatens:** VIP (source 7) already performs a learned, in-training, budget-capped allocation per prompt via a Gaussian process, uncomfortably close to "a learned, budget-capped, in-training verification allocator." The thesis needs a crisp, defensible delta or risks reading as VIP plus a relabeling. None of the frameworks surveyed expose a native "cheap-proxy-then-expensive-judge" switch in the reward API; an allocator must be hand-wired as a wrapper reward function, so implementability at the code level is easy, but none of these frameworks log the telemetry (gold-vs-proxy divergence, judge-call counts per prompt cluster) needed to measure "fewer corrupted rewards" empirically, meaning instrumentation, not the allocator, may be the larger unbuilt piece. The Heteroskedastic Signals paper (source 8) directly threatens the "learned beats fixed" half of the claim: a static, cost-stratified threshold already captures most of the achievable gain in exactly this heterogeneous-reliability setting, so the learned allocator must clear that bar, not a single global threshold. On hardware, TRL's default 0.3 vLLM GPU-memory-utilization and Unsloth's numbers show A100 40GB headroom for 7B GRPO is already thin, so a second scorer competes directly for the VRAM generation needs, weakening the "cheap to bolt on" framing.

## 4. Closest prior work from this angle, and how it differs

The closest prior work from the frameworks/implementability angle is VIP, "Adaptive Rollout Allocation for Online RL with Verifiable Rewards" (Nguyen et al., ICLR 2026, arXiv 2602.01601). It already ships a learned, in-training, per-prompt budget allocator: a Gaussian process predicts per-prompt success probability from recent rollouts, and a convex optimization step distributes a fixed rollout budget across prompts each step, the same "learned, budget-capped, in-training" shape claimed for AVRL. It differs from AVRL in the object being allocated: VIP decides how many rollouts to spend generating on a given prompt (a sampling-budget decision, with the reward function assumed fixed and cheap), while AVRL assumes rollouts are already generated and allocates the verification/scoring budget, i.e. whether to call the expensive judge or accept a cheap proxy reward on a rollout that already exists. VIP's GP models success probability, not proxy-reward error or judge-exploitability, so it has no mechanism for detecting where a majority-vote or small-reward-model proxy is being gamed, which is the reward-hacking-surface half of the AVRL claim that VIP does not address.
